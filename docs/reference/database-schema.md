# Database Schema

PostgreSQL is the single source of truth for transactional data (CLAUDE.md
§10). This document describes the schema **as it exists in the migration
files** — it is generated by reading
`drive-osx-api/src/infrastructure/database/migrations/*.sql` directly, not by
inspecting a running database, so treat those files as the ground truth if
this page and the code ever disagree.

Large binary content (file bytes, attachments) never lives in PostgreSQL —
see [architecture.md §"Storage"](../architecture.md) and CLAUDE.md §11. Tables
below store metadata and references only.

## Connection and migrations

* One database, reached via `DATABASE_URL` (`DATABASE_POOL_MAX` caps pool
  size) — see `drive-osx-api/src/infrastructure/database/pool.ts`.
* Migrations are forward-only `.sql` files in `migrations/`, applied in
  filename order inside one transaction each, on API boot
  (`drive-osx-api/src/infrastructure/database/migrate.ts`). Every applied file
  is checksummed in `schema_migrations`; editing an already-applied file
  throws on the next boot instead of silently reapplying — schema changes are
  always a **new** numbered file (CLAUDE.md §50.19).
* Extensions: `pgcrypto` (`gen_random_uuid()`), `pg_trgm` (fuzzy name search).

| File | Domain |
| ---- | ------ |
| `0001_identity_and_organizations.sql` | Organizations, users, memberships, teams, sessions |
| `0002_files_and_sharing.sql` | Files, versions, shares, upload sessions |
| `0003_collaboration_and_platform.sql` | Mail, meetings, notifications, audit log, domain-event outbox |
| `0004_messaging_and_contacts.sql` | Chat requests, conversations, messages, contacts, presence |
| `0005_contact_detail_fields.sql` | Adds address/website/birthday/department/team/labels to `contacts` |

## Conventions used throughout

* **Primary keys** are `uuid DEFAULT gen_random_uuid()`, except
  `domain_events.id` (generated by application code) and join tables that use
  a composite key (`team_members`, `conversation_participants`).
* **Multi-tenancy** (CLAUDE.md §15–16): tenant-scoped tables carry
  `organization_id uuid NOT NULL REFERENCES organizations`. One shared
  database — tenant isolation is enforced in query code and the authorization
  layer, not by a separate database per tenant.
* **`updated_at`** is maintained by a shared trigger
  (`set_updated_at()`, defined once in `0001`) attached per table — never set
  by application code.
* **Soft delete** is used for `files` (`deleted_at`/`deleted_by`) so trash and
  restore don't need a separate table; `audit_logs` and `domain_events` are
  append-only instead (rows are never updated or deleted by application
  code — CLAUDE.md §34).
* **Full-text search** is a `tsvector` **generated column** (`STORED`), so it
  can't drift from its source columns, indexed with `gin`. Used on `files`
  and `emails`. This is PostgreSQL-native search per CLAUDE.md §13 — no
  external search engine yet.
* **Revocation over deletion**: `shares` rows are kept and marked
  `revoked_at`, not deleted, so grant history survives a revoke.

## 1. Identity and organizations (`0001`)

| Table | Purpose | Notable constraints |
| ----- | ------- | -------------------- |
| `organizations` | Tenants. `type` is `personal` (auto-created per user) or `organization`. Carries `storage_quota_bytes`/`storage_used_bytes` for quota enforcement. | `slug` unique; `owner_id` FK added after `users` exists (circular reference) |
| `users` | Platform accounts. `username`/`email` unique; `password_hash` only, never plaintext. `primary_organization_id` vs `current_organization_id` split lets a user belong to one org by default while acting in another. | `status` ∈ `active/suspended/deleted` |
| `memberships` | User ↔ organization, with role. | Unique per `(organization_id, user_id)`; `role` ∈ `owner/admin/manager/member/guest` |
| `teams` | Named groups within an organization. | Unique `(organization_id, slug)` |
| `team_members` | User ↔ team, with role. | Composite PK `(team_id, user_id)`; `role` ∈ `lead/member` |
| `sessions` | Refresh tokens for login sessions. **Only the hash is stored** — a database leak cannot be replayed. | Partial index on non-revoked rows |
| `password_reset_tokens` | One-time reset tokens, hashed. | Partial index on unused rows |

Every user gets a personal `organization` (`type = 'personal'`) at signup —
"every user starts alone in their own tenant" is the baseline; joining a real
organization is additive on top of that, not a replacement (see
`platform/authorization/access-control.ts`).

## 2. Files and sharing (`0002`)

| Table | Purpose | Notable constraints |
| ----- | ------- | -------------------- |
| `files` | One row per file **or** folder (`type`). Metadata only — `storage_key` points at the object in storage; folders have none. `content_text` is extracted text maintained by the search-indexing worker, kept separate so search never reads from storage. | Unique name per `(organization_id, owner_id, parent_id, lower(name))` among non-deleted rows (`parent_id IS NULL` normalized to a sentinel UUID so the index still applies at the drive root) |
| `file_versions` | Immutable version history. A new version never overwrites the previous object — the old bytes are copied to a `versions/…` key first (see architecture.md), this row records that copy. | Unique `(file_id, version_no)` |
| `shares` | One row per grant — to a `user`, `team`, the whole `organization`, or a public `link`. Link shares store a **hash** of the token, never the token itself. | `CHECK` ties `principal_type` to which of `principal_id`/`token_hash` must be set; unique active grant per `(file_id, principal_type, principal_id)` for user/team shares |
| `upload_sessions` | In-progress resumable/multipart uploads, so an interrupted upload survives a reload (CLAUDE.md §39). | Unique `(user_id, client_token)` — a retried upload with the same idempotency key can't create a duplicate |

Folder sharing inherits: `shares` only ever names the file/folder actually
shared, but `effectiveFileRole()` walks the target's ancestor chain
(`parent_id`) at read time to see if any ancestor folder carries a grant —
there is no `shares` row per descendant.

## 3. Collaboration and platform (`0003`)

| Table | Purpose | Notable constraints |
| ----- | ------- | -------------------- |
| `emails` | Mail messages. `folder` is the mailbox folder (inbox/sent/drafts/trash/spam/archive); `attachments` is metadata-only JSON, bytes live in storage. | Full-text `search_vector` over subject/addresses/body |
| `meetings` | Video-call sessions. Per-meeting policy flags (`allow_screen_share`, `allow_recording`, …) are columns, not a nested config object, so they're directly queryable/indexable. | `code` unique (join code) |
| `meeting_participants` | Who is/was in a meeting. | Unique active participant per `(meeting_id, user_id)` — `left_at IS NULL` |
| `meeting_messages` | In-meeting chat, separate from `messages` (the DM/conversation table) since it's scoped to a meeting's lifetime. | — |
| `notifications` | Per-user notification center entries. | Partial index on unread |
| `audit_logs` | **Append-only** security/audit trail — actor, action, resource, metadata, request context. Never updated or deleted by application code. | Indexed by org, by resource, and by actor, each with `created_at DESC` |
| `domain_events` | Transactional outbox (CLAUDE.md §24): a domain event row is committed **in the same transaction** as the state change that caused it, then dispatched by the worker. `claimed_at`/`processed_at`/`attempts` track delivery. | Partial index on unprocessed rows |

## 4. Messaging and contacts (`0004`, `0005`)

Direct messaging is gated: two users can't exchange messages until a
`chat_requests` row is accepted, which creates the conversation and the
reciprocal `contacts` rows in one transaction — the three tables are designed
to always agree, not synced after the fact.

| Table | Purpose | Notable constraints |
| ----- | ------- | -------------------- |
| `chat_requests` | Pending/accepted/rejected/cancelled introduction between two users. | `CHECK` forbids self-request; unique **pending** request per unordered pair (`least`/`greatest` of the two ids) |
| `conversations` | A DM (`kind = 'direct'`) or group chat. `last_message_at`/`last_message_preview` are denormalized for list ordering without touching `messages`. | — |
| `conversation_participants` | Membership, per-participant `is_muted`/`is_pinned`/`last_read_at` (drives unread counts). | Composite PK `(conversation_id, user_id)` |
| `direct_conversation_keys` | Enforces **one** direct conversation per user pair via a generated, order-independent pair key. | `CHECK (user_a_id < user_b_id)` + unique index on the ordered pair |
| `messages` | Chat messages. Supports threads (`thread_parent_id`) and quote-replies (`reply_to_id`) as two different relationships; `reactions`/`mentions` are inline JSON/array rather than join tables since they're small and always read with the message. | Soft-deleted via `deleted_at` |
| `contacts` | A user's address book. `contact_user_id` links to a real platform account when the contact is one (e.g. created via an accepted chat request); external-only contacts leave it null. `source` explains provenance in the UI. `0005` added `address/website/birthday/department/team/labels`. | `CHECK` forbids self-contact; unique `(owner_id, contact_user_id)` when linked to a real account |
| `user_presence` | Durable "last seen" projection. The **live** heartbeat lives in Redis (CLAUDE.md §12); this row is the rebuildable snapshot that survives a restart. | PK is `user_id` |

## Entity relationships

```text
organizations ──┬── users (via memberships, many-to-many)
                 ├── teams ── team_members ── users
                 ├── files
                 ├── shares
                 ├── emails, meetings, notifications, audit_logs
                 └── conversations, chat_requests, contacts

files (self-referential tree via parent_id)
  ├── file_versions      (1 file : many versions)
  ├── shares             (1 file : many grants; principal = user/team/org/link)
  └── upload_sessions    (optional in-flight upload → completed file)

users
  ├── sessions, password_reset_tokens
  ├── contacts            (owner_id)      — the address book a user keeps
  ├── contacts            (contact_user_id) — appearing in someone else's book
  ├── chat_requests        (requester_id / recipient_id)
  ├── conversation_participants → conversations → messages
  └── meeting_participants → meetings → meeting_messages
```

## What is deliberately not modeled yet

Per CLAUDE.md §46 (introduce infrastructure only on concrete need) and the
audit tracked in `docs/status/audit-and-plan.md`:

* No `calendar_events` table — Calendar is browser-only (TASK-009).
* No tables for Spreadsheet/Presentation/Paint documents — those apps don't
  persist to Drive yet; only File Explorer/Code Editor read and write real
  `files` rows.
* No mail folder/rule tables — Mail Studio's custom folders and filter rules
  are local placeholders; only the `emails` row itself is server-owned.
* No dedicated search engine or vector database — `files.search_vector` /
  `emails.search_vector` (PostgreSQL full text) is the whole search stack for
  now; pgvector is the planned next step if/when semantic search is needed
  (CLAUDE.md §14), not before.

See [reference/applications.md](applications.md) for which application reads
and writes which of these tables today.
